- **YouTube pot token 防護兼容**（M1-42）：真實 YouTube 對 `/api/timedtext` 引入 `pot` 防護後，**任何無 pot 的請求（原始 baseUrl / +fmt=json3 / +srv3 / +vtt）都返回 HTTP 200 + text/html + 空 body**——popup 從 M1-40 的 `missing transcript root` 演進為 `timedtext XML: parse error (not valid XML) — root <html>, (empty body)`。實證三件事：pot 非靜態（不在 `ytInitialPlayerResponse`/`ytcfg`）、由播放器 JS 動態生成且**綁定請求上下文**（複製完整 URL 再 fetch 仍空）、播放器用 **XMLHttpRequest**（非 fetch）發字幕請求。方案「MAIN world 攔截複用」：注入 `yt-timedtext-interceptor`（MAIN world）hook 播放器 XHR，捕獲其已成功（含 pot、已過驗證）的 timedtext 響應，經 `window.postMessage` 橋回 content-script（`timedtext-bridge`），`FetchCaptionSource` 經新端口 `CaptionCaptureProvider` **優先複用**捕獲響應（srv3/json3 自動識別）、無捕獲/解析失敗/空響應回退直接 fetch。繞過 pot 生成——**不重新請求，直接用播放器響應**。教訓：**播放器內部資源請求（XHR/fetch）是擴充無法直接復刻的「最後一手」來源**——與其猜 pot/簽名算法，不如攔截播放器自身成功的請求；**content-script isolated world 看不到 MAIN world 的 XHR/fetch**——必須注入 MAIN world 腳本 + `web_accessible_resources` 放行 + `window.postMessage` 橋；**hook 宿主 XHR 時必須 `apply(this)` 保留實例接收者**（`boundOpen.call(xhr)` 在 jsdom 拋 `'open' called on an object that is not a valid instance of XMLHttpRequest`，brand check 失敗）。
- **捕獲時序修復**（M1-43）：M1-42 在**已登錄 Chrome + 真實 YouTube** 重新構建測試仍失敗——捕獲方案「理論正確但時序全錯」。四斷鏈點 + 對應教訓：**(1) 注入太晚**——`bridge.inject()` 在 `await ensureMounted()`（播放器就緒）之後才執行，播放器早期字幕請求被漏。教訓：**攔截器必須在頁面加載最早期注入**（content-script `start()` 第一行），不能等任何 await。**(2) fetchTracks 跑在播放器請求之前**——orchestrator 抓字幕立即執行、早於播放器發字幕請求，捕獲值恆 null → 一律回退直接 fetch（無 pot → 空 body，問題原樣復現）。教訓：**攔截器 + 立即拉取 = 永遠捕不到**，必須給「等待捕獲」窗口（`waitForCapture(15s)`）——等待捕獲到達並直接解析該捕獲，而非二次讀緩存。**(3) 只 hook XHR**——播放器若改用 fetch 發字幕請求則完全不捕獲。教訓：**必須同時 hook XHR 與 fetch**，兩路並捕。**(4) restart 清空緩存**——`stop()` 調 `bridge.dispose()` 把 latest 清空，熱重啟後永久回退直接 fetch。教訓：**`dispose`（含清緩存）與 `stop`（僅停監聽、保留緩存）必須分離**；熱重啟走 `stop`。另：**E2E 測試盲區的根源是 `web_accessible_resources` 未含 localhost**——Chrome 拒絕載入 MAIN world 腳本（"Resources must be listed in the web_accessible_resources manifest key"），M1-42 的「捕獲鏈路」在 E2E 從未真正運行過，E2E 只驗證了「無捕獲回退」路徑。教訓：**攔截類功能若不把 mock 域加進 WAR matches，E2E 驗證的是死碼**；TEST_PROFILE 構建需同步向 WAR matches 追加 localhost。
- **已修復測試/真實環境暴露的缺陷**：翻譯管線降級事件被吞、mock 站點 `/watch` 路由 404、manifest SW/CS 路徑錯誤、mock 播放器容器 `textContent` 覆寫刪除覆蓋層、content-script fetch 未綁定。
- **LLM 響應 body 讀取失敗診斷區分**（M1-44）：真實使用中 popup 顯示 `LLM translation response is not valid JSON: Failed to fetch`——「Failed to fetch」是網絡層錯誤卻被誤報成 JSON 解析失敗。根因是 fetch 成功（200 頭已收）但 `res.json()` 讀 body 流時連接被中止（本地模型服務發 200 後即斷連/推理異常）。修復：`res.json()` catch 區分 `Failed to fetch`/`NetworkError`（→「connection lost」）與語法錯誤（→「not valid JSON」）。教訓：**HTTP 頭已收到 ≠ 響應完整**——body 讀取階段的網絡錯誤與格式解析錯誤必須分開報，否則誤導用戶排查方向。
- **攔截器注入時序與 SPA 換視頻**（M1-45，真實環境反饋「成功一次→換視頻永久失敗」根因修復）：用戶反饋首次成功一次、換視頻後永久失敗（重載/重裝均失敗）。三層根因與教訓：**(1) content-script 的 `run_at: document_idle` 讓整個 content-script（含攔截器動態注入）都在頁面加載完成後才運行**——首次加載（慢）攔截器碰巧趕在播放器 timedtext 請求前裝好 → 成功；換視頻/切回（有緩存，播放器極快）**請求在攔截器裝好前已發出並完成** → 永遠捕不到 → 回退直接 fetch（無 pot）→ 空 body。教訓：**攔截器必須用 manifest `world:"MAIN"` + `run_at:"document_start"` 直接聲明注入，在頁面最早階段就 hook，動態 `<script>` 注入在 document_idle 場景等同無效**；「首次成功、之後永久失敗」的典型模式就是時序競態——攔截類功能驗證不能只在首次加載驗證，必須測「帶緩存二次加載/SPA 導航」。**(2) YouTube 換視頻是 SPA（pushState），content-script 不重載、orchestrator 不重跑**——換視頻後根本不會重新 fetchTracks。教訓：**SPA 導航（URL `v` 變化）必須由 content-script 主動偵測並熱重啟字幕管線**（`popstate` + patch `pushState/replaceState`，保存原始引用、dispose 恢復）。**(3) 捕獲緩存無視頻身份**——`bridge.latest` 是上一視頻的捕獲，會被誤貼到新視頻。教訓：**跨資源複用的緩存必須綁定資源身份並校驗**（`videoId` 匹配才複用；無身份保守接受、明確不同才拒絕）。
- **攔截器 postMessage 早於 bridge 監聽器註冊**（M1-46，M1-45 引入的新競態根因修復）：M1-45 把攔截器提前到 document_start 後，連「首次成功」也消失了（用戶反饋：`window.__aiTransTimedtextInterceptorInstalled` 返回 `true` 確認攔截器已運行，popup 仍報 pot 空響應）。根因：**攔截器在 document_start（MAIN world）捕獲響應後 postMessage，但 bridge 的 message 監聽器在 content-script（document_idle）才註冊**——帶緩存二次加載時播放器 timedtext 請求在 **document_idle 之前**就發出 → 攔截器捕獲並 postMessage，**但監聽器尚未就位 → 消息永久丟失** → `waitForCapture(15s)` 超時 → 回退 fetch。M1-45 之前的「首次成功」是動態注入（document_idle，注入與監聽幾乎同時）的巧合；M1-45 後攔截器**永遠比監聽器早** → 從「碰運氣」變「必然失敗」。教訓：**(1) 拆分「注入時序」與「消息到達時序」**——攔截器提前注入解決了「hook 裝好前請求已發」，但引入了「postMessage 發在監聽器註冊前」；必須**讓捕獲可被晚到的監聽器收到**（周期重播 lastCapture，1.5s 遠小於 waitForCapture 15s 窗口）。**(2) E2E 時序盲區**——mock 播放器請求時機設計在 content-script 就緒之後，從不模擬「播放器先於 document_idle 發請求」，這類「捕獲早於監聽器」的競態在 E2E 永不暴露；**攔截類功能的 E2E 須覆蓋「外部事件先於內部初始化」場景**。**(3) 調試輔助是真實環境驗證的必要條件**——暴露 `__aiTransTimedtextRequests`（命中計數）與 `__aiTransTimedtextLastCapture`（捕獲對象），真實環境一鍵定位「hook 沒觸發」vs「捕獲到但解析/複用斷」，避免盲猜。
- **消息通信機制與字幕模組驅動修復**（M1-47，真實環境反饋「捕獲成功但字幕不顯示」根因修復）：用戶反饋捕獲成功（`Capture count: 1`、`__aiTransTimedtextLastCapture` 有值）但字幕不顯示，console 出現 `LLM translation response body read failed (connection lost): Failed to fetch`。三層根因與修復：**(1) 消息通信失敗**——content-script 的 `window.postMessage` 與 MAIN world 的 `globalThis.addEventListener('message')` 在 isolated world 與 MAIN world 之間通信失敗（`__aiTransTargetLang: undefined`），導致字幕模組驅動未觸發。修復：改用 `CustomEvent`——content-script 用 `document.dispatchEvent(new CustomEvent('ai-trans:set-target-lang', { detail: { targetLang } }))`，interceptor 用 `document.addEventListener('ai-trans:set-target-lang', ...)`，避免跨 world 通信問題。**(2) 字幕模組驅動重試不足**——`MAX_RETRIES=20`（20 秒）在 YouTube 播放器加載較慢時不足，且沒有立即觸發機制。修復：`MAX_RETRIES` 增至 60（60 秒）；`resetAndRedriveCaptionModule()` 立即嘗試一次 `ensureCaptionModuleLoaded()`；收到 `SET_TARGET_LANG_EVENT` 消息時立即調用 `resetAndRedriveCaptionModule()`。**(3) 翻譯失敗時字幕完全不顯示**——LLM 翻譯服務連接失敗時，錯誤冒泡到策略鏈但不顯示任何字幕。修復：`NativeCaptionStrategy.run()` 添加 try-catch 捕獲翻譯錯誤，失敗時顯示原文字幕（`translatedText` 設為 `sourceText`）並發送 `engine-degraded` 事件。教訓：**(1) isolated world 與 MAIN world 通信必須用 DOM 事件**——`window.postMessage` 在跨 world 場景下不可靠，`CustomEvent` 通過 DOM 事件系統傳播不受 world 隔離影響。(2) 字幕模組驅動必須有足夠的重試窗口和立即觸發機制**——YouTube 播放器加載時間不確定，20 秒重試不足；立即觸發 + 60 秒重試確保驅動成功。(3) 翻譯失敗必須降級顯示原文**——用戶寧可看到原文字幕也不願看到空白；降級時發送 `engine-degraded` 事件讓 popup 顯示原因。
- **LLM 翻譯直接 fetch 架構優化**（M1-48，service worker 代理移除）：用戶反饋 LLM 翻譯極慢——fetch 實際完成僅 19-25ms，但消息投遞延遲 138s+。根因：Chrome MV3 service worker 被掛起後，`chrome.runtime.sendMessage` 和 `port.postMessage` 響應被延遲到 SW 喚醒（Chrome 對 SW 有 30s-5min 不等的掛起策略）。原方案嘗試 `alarms` keepalive（0.4 分鐘週期）+ port 長連接均無法根治（SW 仍會被強制掛起，消息排隊等待喚醒）。**根本解決方案：content script 直接 fetch**——manifest 已有 `host_permissions`（`http://127.0.0.1/*`、`http://localhost/*`），content script 在 ISOLATED world 可直接 fetch localhost 無需 CORS 預檢（host_permissions 授予跨域權限），且不受 SW 掛起影響。`LLMTranslationProvider` 從 `chrome.runtime.sendMessage` / port proxy 改為 `globalThis.fetch` 直接調用。移除：(1) service-worker `translation:fetch` 消息處理（~45 行）；(2) `alarms` keepalive 機制；(3) `onConnect` port proxy（~60 行）；(4) manifest `alarms` 權限。Service worker 從 156 行精簡到 46 行，僅保留 `config:get`/`config:set` 配置管理。教訓：**(1) MV3 service worker 不適合做實時消息代理**——SW 掛起是不可控的 Chrome 行為，任何依賴 SW 即時響應的設計都會在掛起後崩潰；**(2) host_permissions 可讓 content script 繞過 CORS**——之前誤以為 content script 無法直接 fetch localhost 是錯誤認知，ISOLATED world 的 content script 有 host_permissions 即可跨域；**(3) 架構選擇優先考慮「不依賴可掛起組件」**——比嘗試「防止掛起」更可靠。
- **字幕背景樣式增強**（M1-49）：用戶反饋純白/純黑視頻上字幕難以辨識。方案：**(1) 默認樣式優化**——白字（`#ffffff`）+ 黑色環繞描邊（`text-shadow: 0 0 4px #000, 0 0 2px #000`）+ 灰黑半透明背景（`rgba(32, 32, 32, 0.7)`），確保極亮視頻（黑色描邊凸顯白字）和極暗視頻（白字+深色背景對比）均清晰可讀。**(2) Options 背景設置 UI 重構**——原 `#style-bg` 文本輸入框改為下拉預設選擇器（無背景/半透明灰黑推薦/半透明黑/自定義）+ 自定義區域（`<input type="color">` + `<input type="range">` 透明度 0-100%），選「自定義」時展開顏色+透明度控件。**(3) 向後兼容**——舊配置 `transparent` 自動映射為「無背景」預設，不影響已有用戶。教訓：**(1) 字幕可讀性需要多層對比保障**——單靠背景色或文字顏色不足以應對極端視頻（純白/純黑），需要「文字顏色 + 描邊 + 背景」三重保障；**(2) 設置界面應提供預設+自定義雙模式**——預設覆蓋 90% 場景，自定義滿足特殊需求，比純文本輸入更友好。
- **中央調試日誌門控**（M1-51）：M1-50 逐點降壓治標不治本——新增 `src/infrastructure/debug-log.ts` 中央門控：`DebugLogCategory` 八分類（overlay/llm/capture/pipeline/strategy/content/bridge/interceptor），`diagLog(category, ...)` 僅在對應分類開啟時輸出（前綴 `[AI_Trans:diag][category]`），`DEBUG_LOG_OFF` 全關為預設；`EngineConfig.debugLog` 持久化，Options 新增「調試日誌」分區八分類 checkbox；content-script 啟動/熱重啟時 `setDebugFlags` 並經 `CustomEvent('ai-trans:set-debug-flags')` 中繼給 MAIN world 攔截器。全庫既有 `console.log` 診斷改走 `diagLog`，**錯誤/降級（console.warn + recordDiagnostic）不受開關影響**（§5.6 不靜默）。教訓：**(1) 日誌治理要「中央門控」而非逐點降壓**——分類開關讓開發者按需開啟，普通用戶零噪音；**(2) MAIN world 攔截器無法訪問 chrome.storage**——配置必須經 DOM 事件（CustomEvent）中繼，與 M1-47 的 set-target-lang 同一機制；**(3) 診斷日誌 ≠ 錯誤日誌**——`diagLog` 只門控流程診斷（console.log），錯誤/降級必須始終可見。
- **字幕延遲優化**（M1-52）：用戶反饋長視頻（數百段字幕）翻譯遲遲不顯示——單次請求整片 LLM 輸出耗時數分鐘，且中途任一失敗全片無字幕。四項修復：**(1) 超時覆蓋 body 讀取**（舊實現收到響應頭後即 clearTimeout，body 流掛死時超時永不觸發——M1-47 的 connection lost 場景根因）；**(2) 分塊翻譯**（`CHUNK_SIZE=60` 逐塊請求，單塊輸出控制在數十秒內）；**(3) 漸進 emit**（`translateStream` 每塊完成 emit 累計全量，首個 emit 映射 `segments-ready`、後續映射 `segments-updated`，渲染層 5-10s 內先見首塊）；**(4) LRU 快取**（key=`model|targetLang|djb2Hash(塊源文)`，100 條上限，storage.onChanged 偵測 engineConfig 變更全量失效）；**(5) 瞬態失敗重試**（網絡中止/超時/429/5xx/body/parse 重試 ≤2 次 500ms→1500ms 退避，耗盡該塊原文兜底不中斷；永久失敗立即拋錯走降級）。教訓：**(1) 大請求要「切塊 + 漸進交付」**——把「整片翻譯」變成「首塊秒級可見、後續增量替換」，體驗質變；**(2) 超時必須覆蓋整個響應生命週期**——「響應頭已收到」不代表「body 已讀完」，timer 清理必須放 finally；**(3) 快取鍵要含模型與語言**——換模型/換語言鍵空間不同才不會誤命中；**(4) 重試要區分「瞬態」與「永久」失敗**——4xx 非 429 與 choices 缺失重試無用，重試只救得回網絡抖動。
- **ASR 依賴注入修復 + 自定義模型路徑配置**（M2-16）：用戶反饋無字幕視頻的 ASR 字幕未生成，且 README/Options 仍帶「M2 待實現」字樣。三層根因與修復：**(1) RealtimeASRStrategy 從未注入依賴**——`orchestrator.ts` 和 `composition.ts` 都未調用 `inject()`，導致 `isApplicable()` 因 `if (!this.deps)` 恆返回 false，策略永不執行。修復：`orchestrator.start()` 中遍歷 `registry.strategies` 找到 `RealtimeASRStrategy` 實例並注入 `{audioSource, asrProvider, translationProvider, vadThreshold}` + 調用 `warmup()`；ASR provider 取用從硬編碼 `'asr'` key 改為 `registry.asr.values().next().value`（兼容 `local-whisper`/`cloud-asr-openai`/`cloud-asr-deepgram` 不同 engineId）。**(2) 自定義模型路徑未暴露**——`LocalWhisperASR` 支持 `modelPath` 參數但 Options UI 未提供輸入框。修復：`ASRConfig` 新增 `customModelPath?: string`（優先於 `modelTier`）；`options.html` 加自定義模型路徑輸入框；`options.ts` 讀寫；`composition.ts` `buildASRProviders` 傳入 `customModelPath`。**(3) M2 字樣殘留**——`README.md:115`「for future M2」、`README.zh-Hant.md:115`「供未來 M2」、`options.html:52`「M2 起用」已清理。教訓：**(1) 依賴注入必須在組裝點顯式調用**——`inject()` 方法存在但未被調用等同於死碼；**(2) Registry 的 Map key 不應硬編碼**——不同 provider 的 `engineId` 可能不同，應遍歷 values 或按類型查找；**(3) warmup 必須在 start 時調用**——`LocalWhisperASR.warmup()` 下載模型到 IndexedDB，不調用則首次 `transcribe()` 拋「not warmed up」。
- **CSP 違規修復（ASR warmup `new Function` 動態 import）**（M2-17）：用戶反饋控制台出現 CSP 錯誤：`Evaluating a string as JavaScript violates the following Content Security Policy directive because 'unsafe-eval' is not an allowed source of script`。根因：`src/adapters/asr/local-whisper.ts:55` 使用 `new Function('modulePath', 'return import(modulePath)')` 動態導入 `@huggingface/transformers`，觸發 Chrome 擴展 CSP 禁止 `unsafe-eval`。修復三管齊下：**(1) 直接 import 替代 new Function**——`local-whisper.ts:51-75` 改為 `await import('@huggingface/transformers')`，加 `@ts-expect-error` 註釋（可選依賴可能未安裝）；**(2) build.mjs 標記 external**——esbuild 配置加 `external: ['@huggingface/transformers']`，保留動態 import 不被打包（運行時從 node_modules 加載）；**(3) Vitest config 加 mock**——`vitest.unit.config.ts` 和 `vitest.integration.config.ts` 的 `resolve.alias` 將 `@huggingface/transformers` 映射到 `test/support/mock-huggingface-transformers.ts`（空 pipeline 函數，拋「not available in test environment」），避免測試環境因可選依賴未安裝而崩潰。教訓：**(1) Chrome 擴展 CSP 默認禁止 `unsafe-eval`**——`new Function`、`eval`、`setTimeout/setInterval` 的字符串參數都會觸發 CSP 錯誤；**(2) 可選依賴的動態 import 必須在構建工具中標記 external**——否則 esbuild 會嘗試打包未安裝的模塊；**(3) 測試環境需要 mock 可選依賴**——Vitest 的 `resolve.alias` 可將可選依賴映射到 mock 模塊，避免 `Failed to resolve import` 錯誤。⚠️ **external 方案後續被 M2-18 推翻**——Chrome content script 無 node_modules 解析路徑，external 保留的裸 import 在運行時無法解析。
- **ASR warmup 模塊解析 + 字幕攔截器 DOM 解析修復**（M2-18，真實 YouTube 雙阻斷修復）：用戶反饋真實 YouTube 頁面兩個阻斷：(1) ASR warmup 失敗——`@huggingface/transformers` 模塊無法解析（`Failed to resolve module specifier`）；(2) 字幕攔截器 `player.getOption('captions', 'tracklist')` 持續返回空陣列。**問題 1 根因**：M2-17 的 `external` 方案保留裸 `import('@huggingface/transformers')`，但 Chrome content script（IIFE bundle）無 node_modules 解析路徑；且包雖在 `optionalDependencies` 但從未 `npm install`。修復：`npm install` + 移除 `external` → esbuild 將 transformers 完整打包進 IIFE。**問題 2 根因**：`getOption('captions', 'tracklist')` 在真實 YouTube 持續返回 `[]`。修復：新增 `getCaptionTracksFromPlayerResponse()` 從 DOM `<script>` 標籤解析 `ytInitialPlayerResponse`（支持 JS 賦值與純 JSON 兩種格式）作為首要來源，`getOption` 降為備用。教訓：**(1) Chrome content script 的模塊解析 ≠ Node.js**——`external` 保留的裸 import 在 IIFE bundle 中無法解析，必須打包進 bundle；**(2) `optionalDependencies` 不會自動安裝**——`npm install` 必須顯式執行；**(3) 播放器 API 不可靠時直接解析頁面數據**——`ytInitialPlayerResponse` 是 YouTube 頁面內嵌的結構化數據，比 `getOption` 更可靠。
